# Обновление мест проведения турниров

## Дополнение: вариант «Другое» (миграция 034)

В админке при создании или редактировании турнира можно выбрать «Другое» и
заполнить имя заведения, адрес и полную ссылку на карту (http/https). Все три поля
обязательны. При редактировании существующего турнира нажмите «Сохранить место»:
до этого введённые данные остаются черновиком. При создании они сохраняются вместе
с турниром. Разовая площадка не добавляется в общий список адресов клуба.
В приложении игрока она видна на главной, в расписании и на странице турнира;
«Построить маршрут» открывает введённую ссылку.

Если 033 уже применена, нужна **только новая миграция 034**, до запуска нового backend.
Она добавляет `custom_venue`, расширяет допустимые площадки и проверяет заполненность
данных. Существующие Мансарда и Everest, записи игроков, оплаты и статусы не меняются.

После публикации обновлений в ветках, в `/data/admin-back-ts`:

```bash
git fetch origin
git show origin/tournament-venues:apps/admin-back/db/migrations/034_tournament_custom_venue.sql > /tmp/nuts-034-tournament-custom-venue.sql
sudo -u postgres psql -d "nuts-poker" -X -v ON_ERROR_STOP=1 -f /tmp/nuts-034-tournament-custom-venue.sql
```

Ожидается завершение `COMMIT`. При ошибке блокировки транзакция откатится;
повторите миграцию до выкладки кода. Успешную миграцию можно применить повторно.

Затем подтяните обновления текущей ветки (`git pull --ff-only`) в обоих репозиториях,
пересоберите backend, player-web и admin-ui и перезапустите их штатным способом.
Зависимости не менялись. Не собирайте player-web/admin-ui поверх каталога сборки
работающего приложения: используйте отдельный релиз или остановите соответствующий
интерфейс на время сборки. PostgreSQL и Redis останавливать не нужно.

Выбирайте «Другое» после обновления обоих интерфейсов; перезагрузите старые вкладки.
Старые версии backend/player-web не умеют отображать произвольную площадку и могут
показать Мансарду. Если уже используется «Другое», откат на старый код требует сначала
решить, какой корректный адрес показывать игрокам. Колонки при откате не удаляйте.

Проверка: 267 тестов backend/player-web, TypeScript и production-сборки. На
изолированной БД проверены повторная миграция, сохранение старых данных, создание и
редактирование своей площадки, чтение, переключение обратно на готовую площадку,
защита от неполных данных и сохранение адреса при обычном обновлении старым клиентом.
В Chrome на тестовых данных проверены создание, редактирование и повторное открытие,
ошибка сохранения и отмена черновика, мобильная форма, возврат к готовой площадке,
адрес и маршрут игрока на главной, в расписании и на странице турнира.

## Первоначальная выкладка двух площадок (миграция 033)

Ветки:

- `admin-back-ts`: `tournament-venues`, от `player-web/remove-decorative-symbols`.
- `admin-ui`: `tournament-venues`, от `main`.

Справочник содержит две площадки: Мансарда Лаунж-Бар и Everest Mansion
(Житная ул., 4). В БД хранится идентификатор площадки, а адрес и ссылка на карту
берутся из `packages/schemas/src/venues.ts`. Админка получает справочник с API.

## Что происходит с существующими турнирами

Миграция `033_tournament_venue.sql` добавляет только колонку `venue_id`.
Все существующие турниры, включая открытые и идущие, получают `mansarda`.
Идентификаторы, даты, статусы, игроки, оплаты и результаты не меняются.
Текущее состояние игры и записи в Redis не затрагиваются.

Смена места через `PATCH /api/tournaments/:id/venue` обновляет только эту
колонку и добавляет запись в журнал действий. Она не вызывает запуск или
завершение турнира, изменение финала месяца, пересчёт рейтинга или удаление игроков.
Обычные сохранения из старой админки не перезаписывают выбранную площадку.
Создание турнира без `venueId` по-прежнему выбирает Мансарду.

## Порядок выкладки

Команды ниже рассчитаны на опубликованные ветки. Локальные ветки сначала нужно
закоммитить и отправить. Применяйте команды в каталогах соответствующих репозиториев.

1. Проверьте, что на сервере нет несохранённых изменений. Сделайте резервные копии
   PostgreSQL и Redis штатным способом. Сохраните число записанных игроков для
   нескольких открытых турниров для контрольной сверки.

2. **Сначала примените только миграцию 033, пока работает старый backend.**
   Предыдущие миграции до 032 уже должны быть установлены. Не запускайте заново
   `schema.sql` и все исторические миграции: среди них есть заполнение данных.
   `POSTGRES_URL` ниже должен быть экспортирован из тех же настроек, что использует
   рабочий backend; `psql` сам не читает `.env` приложения.

   ```bash
   git fetch origin
   git show origin/tournament-venues:apps/admin-back/db/migrations/033_tournament_venue.sql > /tmp/nuts-033-tournament-venue.sql
   psql "$POSTGRES_URL" -X -v ON_ERROR_STOP=1 -f /tmp/nuts-033-tournament-venue.sql
   ```

   В миграции есть транзакция и ограничение ожидания блокировки в 5 секунд.
   Если она не смогла получить блокировку, ничего не выкладывайте: повторите
   миграцию в более спокойный момент. Повторное успешное применение безопасно.
   Не запускайте новый backend до успешного завершения миграции.

   Проверка:

   ```sql
   SELECT venue_id, status, count(*)
   FROM tournaments
   GROUP BY venue_id, status
   ORDER BY venue_id, status;
   ```

3. Обновите backend и приложение игрока. Используйте прежние переменные окружения,
   адрес API, порты и способ запуска. Для сборки из корня `admin-back-ts`:

   ```bash
   git switch tournament-venues
   git pull --ff-only
   bun install --frozen-lockfile
   bun run build
   ```

   Затем штатно перезапустите backend, после него `player-web`.
   Если production-процесс работает с `--hot` или автоматически перезапускается
   при изменении файлов, готовьте отдельный каталог релиза и переключайте его
   после миграции и сборки. Не собирайте Next.js поверх `.next` работающего
   приложения: используйте отдельный каталог релиза или короткое окно остановки
   только приложения игрока. PostgreSQL и Redis останавливать не нужно.

4. Обновите и соберите `admin-ui`, затем разверните его обычным способом:

   ```bash
   git fetch origin
   git switch tournament-venues
   git pull --ff-only
   pnpm install --frozen-lockfile
   pnpm build
   ```

5. Обновите страницы в браузере. Убедитесь, что старые турниры показывают Мансарду,
   количество записавшихся игроков совпадает, а новая админка загружает обе площадки.
   Только после обновления обоих интерфейсов выбирайте Everest для нужных турниров.
   В уже открытой вкладке со старым JavaScript ссылка ещё может вести на Мансарду,
   пока игрок не перезагрузит страницу. Это не влияет на его запись.

6. В админке место задаётся на шаге «Информация» при создании турнира. В существующем
   турнире откройте вкладку «Турнир», поле «Место проведения»; выбор сохраняется сразу.
   Проверьте адрес и «Построить маршрут» на странице того же турнира в приложении игрока.

Краткий перезапуск API может временно прервать запросы, но сам по себе не удаляет
сохранённые записи. Не очищайте Redis, не пересоздавайте турниры и не меняйте их
статус ради этой выкладки.

## Откат

При откате кода оставьте колонку и данные площадок в БД: старый backend их игнорирует.
Не удаляйте колонку на работающем приложении. Если уже назначены турниры в Everest,
не возвращайте старое приложение игрока без отдельного плана информирования:
оно содержит только ссылку на Мансарду, хотя записи игроков останутся на месте.

## Проверки реализации

- Тесты схем и API проверяют старые запросы без площадки, выбор Everest,
  отказ для неизвестной площадки, сохранение статуса и отдельную операцию смены места.
- На изолированной PostgreSQL-совместимой БД PGlite проверены повторная миграция,
  сохранение старых полей, записей и оплат, создание старым/новым клиентом,
  чтение площадки и сохранение Everest при обычном обновлении старого клиента.
- Рабочая база при разработке не использовалась; миграция на ней не применялась.
- Production-сборки backend, player-web и admin-ui и проверки TypeScript проходят.
  В полном наборе backend/player-web: 261 успешный тест.
- В Chrome на тестовых данных проверены адреса регистрации, «О клубе» и Q&A,
  маршрут Everest и старый ответ без площадки, создание турнира, смена площадки
  в десктопной и мобильной админке, возврат выбора при ошибке сохранения.
